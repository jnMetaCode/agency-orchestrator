# 本地任务登记存储

`FileJobStore` 是任务服务的底层文件存储适配器，通过包入口导出。它保存任务身份和状态，不自行启动工作者或调用模型。Studio 已将 /api/run 的登记与结束状态接入；Studio 已支持同一服务实例内的后台运行、事件缓冲及刷新重连；服务重启后的自动续跑仍未实现。

## 接口与数据

- `create(requestId, snapshot, { displayName? })`：返回 `{ job, created }`。同一 requestId、同一快照复用已登记任务；改变请求后复用该 ID 会抛 `JOB_CONFLICT`。请求 ID 只存 SHA-256。
- `get(id)` / `list(limit)`：读取已提交快照；返回独立副本，调用者修改不会写回。列表默认 50、最多 200，但底层会扫描全部记录。
- `transition(id, status, expectedRevision)`：只允许声明的状态转换，并拒绝旧版本写入。成功时 revision 和事件 sequence 一起递增；相同状态和当前版本为无变更返回。终态不复活，重跑应创建新逻辑任务。
- `events(id, afterSequence)`：返回快照、后续事件和 resetRequired；默认保留最近 128 条。游标过期时告知用快照重建，而不是静默遗漏旧事件。

`JobSnapshot` 只接受 requestHash、workflowHash、briefRevision、connectionProfileId、connectionRevision。哈希为 64 位小写十六进制，其余字段是短标识符；不接受完整请求、配置、URL 或 credential 字段。调用方必须根据完整规范化逻辑请求（输入、工作流、约束、连接 revision、策略等）计算 requestHash，不能只传工作流哈希后声称能够识别输入变化。字段校验防止常见误传，不可能识别所有故意伪装成标识符的秘密。

状态写入只是登记。调用 `transition(..., 'paused', ...)` 不会实际暂停进程；未来 JobService 必须在执行器确认暂停后再登记这个状态。中断状态不自动转为 running，是否继续付费执行需要恢复协议。

## 文件与并发保证

使用专用可写目录（例如应用数据目录下的 jobs 子目录），不要混用用户文档目录。新目录按 0700 创建，记录和暂存文件为 0600。既有目录权限不自动收紧，操作方需保证其访问权限。

每任务一个 JSON 文件，包含快照、revision 和有界事件；文件先独占暂存、写入/fsync、关闭，然后原子替换。所有合作写入者使用目录互斥锁；创建时扫描记录并检查请求 ID 摘要，避免引入第二份幂等索引的多文件一致性问题。进程强杀后的下次写操作回收符合保留格式的普通暂存文件；以已提交记录为准，不把暂存内容当作新状态。

支持同机、同文件系统、遵守相同锁的低流量场景；不保证非协作外部写入安全、跨机器分布式调度或系统掉电后的完整持久性。文件 fsync 不等于父目录元数据已经在断电前持久化。锁忙时当前借用配置锁的占用错误，调用方应明确处理重试；后续服务接入需统一稳定错误码。

创建和列表扫描复杂度随历史记录增长；旧任务记录没有自动删除策略。记录仍存在时才保留创建幂等；手工删除记录会失去该请求 ID 的去重保证。事件保留有界不等于磁盘任务数量有界。大规模任务应迁移到具备索引、事务与保留策略的数据库适配器。

损坏、链接、非普通文件和超大记录会拒绝读取，解析错误不回显原文。创建扫描遇到损坏记录也会停止，以免不知道其幂等键就重复创建任务；不自动删除或隔离可能仍包含任务身份的文件。

## 实现边界

已接入 `/api/run` 启动前登记和终止状态、查询 API 与任务记录页面。关闭页面只取消订阅，运行继续；显式取消通过 `/api/run-cancel` 终止进程。同一服务实例保留运行事件，可刷新后重新订阅；这不等于服务崩溃后的持久恢复。

人工输入使用引擎为每次问题生成的随机 `inputRequestId`，提交同时匹配 `runId`、`stepId` 和问题标识。回答以单行 JSON 帧写入 stdin，文本中的换行不会变成下一次回答。服务端写入前消耗当前问题，重复、过期和取消后的提交会拒绝；`input-accepted` 事件使重连回放能够清除已回答的问题。旧页面缺少问题标识时需要刷新。单次回答最大 64 KiB（UTF-8）。CLI 的普通文本输入方式不变。

问题标识和等待请求目前只保存在服务内存中，不落入任务登记文件；任务登记已在收到问题时进入 `waiting_input`、接受回答时回到 `running`；不保存当前等待节点、问题正文或回答内容。状态写入失败不会阻塞输入，页面会提示记录可能滞后。若没有回答却以成功码退出，按失败记录；回答已被接受但其状态写入失败时，完成收尾会修正滞后的等待状态。没有真实 worker 所有权、租约、fencing、步骤 checkpoint 或统一队列。写管道失败时回答可能已经部分送达，接口返回 `INPUT_DELIVERY_UNKNOWN`，不自动重发，也不承诺跨进程或崩溃后的 exactly-once。输出标记通道不具备独立认证，随机问题标识不能解释为对恶意输出的完整隔离。

## 人工输入失败后的状态核对

`GET /api/live-runs/:runId/input` 返回当前服务内存中的 `{ active, pendingInput }`，响应禁止缓存。只返回仍活动、未取消运行的当前问题；已消耗、结束或取消的问题返回 null。运行已从内存过期或服务重启后返回 `RUN_NOT_LIVE`。这是等待请求查询，不是引擎已处理回答的回执：null 不能证明 stdin 中的回答已被引擎执行。

Studio 提交失败后只查询当前问题，不自动重新发送回答。发送期间禁止重复点击；草稿不会在点击提交时清空，同一问题验证失败或重新查询时可保留。下一次问题使用不同组件标识，避免把旧草稿带入新审批。用户也可使用“刷新待回答问题”手动核对。查询以本地版本校验防止迟到的响应覆盖新的实时问题、另一轮查询或已结束的运行。查询再次失败时不会恢复一个可能已经消耗的旧问题。
